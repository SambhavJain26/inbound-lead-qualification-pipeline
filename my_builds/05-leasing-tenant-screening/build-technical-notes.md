# Build Technical Notes — Leasing & Tenant Screening

Last updated: 2026-09-12

How this one was actually assembled, what broke, and what I would do differently. Written for
someone technical who wants to know whether the thing is real.

## Shape

Four n8n workflows, 71 nodes, one Postgres database, zero npm dependencies.

| Workflow | Nodes | Does |
|---|---|---|
| WF1 `leasing-front` | 28 | Lead intake, grounded FAQ, pre-qualification, tour booking, application handoff |
| WF2 `application-and-verify` | 18 | Application intake, document extraction, income verification, criteria engine |
| WF3 `telegram-router` | 10 | The only Telegram Trigger. Manager decisions |
| WF4 `lease-and-signature` | 15 | Lease generation, DocuSign, signature return, unit status |

Workflow JSON is generated by builder scripts rather than edited in the n8n UI. Shared logic
lives in two libraries that get inlined into Code nodes at build time, so there is exactly one
copy of the guardrails, the pre-qualification gate, and the criteria engine.

Committed JSON carries placeholders only (`__POSTGRES_CREDENTIAL_ID__`, `__TUNNEL_URL__`, …).
The import script resolves them from `.env` and the running instance into an ignored `tmp/`
copy. No local identifier, address, or key is ever committed.

## What Is Real And What Is Simulated

Real, running against live services:

- **Plaid Sandbox** for income verification — the genuine API, free, unlimited test data
- **DocuSign developer sandbox** for e-signature, with per-envelope Connect configuration
- **Cal.com** for tour booking, including the booking webhook
- **OpenAI** for document extraction and grounded answers
- SMTP/IMAP for mail, Postgres for state, Telegram for decisions

Simulated, and labelled `(MOCK)` at every node, record, and diagram box:

- **Credit, eviction, criminal records.** Not a budget decision. Consumer reports require FCRA
  permissible-purpose credentialing: a bureau contract, a registered business, and typically a
  site inspection. There is no developer sandbox at TransUnion or Experian. The mock returns
  fixtures shaped to the public ShareAble v3 schema, so the swap is one node.
- **Identity document check.** Plaid Sandbox performs no OCR, so its identity product returns
  canned results and demonstrates nothing.
- **Smart-lock entry codes.** Paid hardware and subscription.
- **The listing-site feed.** Zillow has no public lead API — but it does deliver leads by
  email with an anonymised relay address, so parsing a lead email is the genuine integration.

## The Core Design Decision

The criteria engine is deterministic JavaScript reading manager-configured thresholds from a
config table. It never calls a model.

This is not caution for its own sake. HUD's May 2024 guidance says screening tools should
*implement, rather than set* the provider's policies and offer customizable criteria, and it
states plainly that a decision being algorithmic does not shield it from civil-rights law. An
AI that scores applicants is the thing the regulator is worried about; published criteria
applied identically with a recorded evidence trail is the thing it describes approvingly.

So the division is strict:

- **The model** answers questions from a grounded knowledge base, extracts fields from
  documents with a citation per value, and drafts messages.
- **The engine** classifies: `meets_criteria`, `conditional`, or `does_not_meet`, with the
  document, field, and value behind every result.
- **A person** decides.

The test suite asserts this rather than trusting it. One test serialises the engine's entire
output and fails if it contains the words approve, deny, reject, recommend, score, risk, or
rank.

## The Fraud Detection, Concretely

Plaid Sandbox returns a fixed income for every applicant: `$2,306` biweekly, so `$4,996.33`
a month. That constraint shaped the fixtures rather than the other way round — the two demo
applicants are separated by **rent**, not income:

| | Unit | On paper | Verified | Outcome |
|---|---|---|---|---|
| Maya | $1,650 | 3.03x | 3.03x | meets criteria |
| Devon | $1,950 | **4.00x** | **2.56x** | does not meet |

Devon's pay stub claims $7,800/month. His deposits say $4,996. A 56% overstatement that
would have sailed through a human reading the PDF.

The comparison is three-way on purpose — what the applicant typed, what the document says, and
what the bank shows — because those three disagreeing in different combinations means
different things.

Capturing the real Plaid response happened in Stage 2 rather than Stage 4 as planned,
specifically because the fixtures had to be built around the real number. That reordering was
worth it; building fixtures first would have meant rebuilding them.

## Testing

38 unit tests across the two libraries, run outside n8n, plus an end-to-end gate per stage.

The end-to-end gates matter more than they look. Every failure that actually cost time in this
build — a dropped query parameter, a JSON schema that was never sent, an empty email, a
form submitting empty fields — passed every static check and only appeared when a real message
went through. The Stage 3 gate sends real mail through two real mailboxes and takes four
minutes, which is a fair price.

Two checks in it are compliance assertions rather than plumbing:

- every dollar figure in an AI-generated reply is re-derived and must appear in the unit facts
- the pre-qualification evidence trail must still carry the `unverified` label and contain no
  decision language

Those are claims made to prospects, so they are tested rather than assumed.

## What Broke

Almost none of the difficulty was in the logic. It was in n8n's own conventions, and nearly
every one failed **silently** or reported something misleading.

**Postgres query parameters, twice over.** The node flattens an array expression with
`if (item === undefined) continue`, so a single absent value shortens the parameter list and
Postgres reports `there is no parameter $5`. Coercing with `?? ''` fixes that and introduces
the second half: `NULLIF($n,'')` fails with `invalid input syntax for type integer: ""`,
because Postgres infers an untyped parameter's type from its surrounding context and parses
the empty string as an integer before `NULLIF` runs. The fix is `NULLIF($n::text,'')`. Both
halves are needed.

**The OpenAI JSON schema was never being sent.** `options.textFormat.textOptions` must be an
object, but the field's own default shows an array. Passing an array means no format is sent,
the model returns prose, and nothing errors anywhere. Found by reading the node's source.

**Form Triggers submit `field-0`, `field-1`, …** in declaration order, not by label, and map
them back on arrival. Posting the labels is accepted and every value arrives `null` — the
submission succeeds, the workflow runs, and the data is empty. The submit script now reads
field order out of the built workflow so it cannot drift.

**Postgres nodes drop binary data**, so an uploaded file has to reach the extract node before
any database node. WF2 is one sequential chain for this reason.

**`httpCustomAuth` is a generic credential type**, not a predefined one. Declared wrongly it
applies no auth at all and the API reports the credentials as missing, as though they were
never configured.

**DocuSign's `eventNotification.events`** requires `deliveryMode: "SIM"` and `eventData`
together. Omit either and it rejects the entire envelope.

**The Telegram Trigger validates a secret header** derived as `${workflowId}_${nodeId}`.
Worth knowing when driving the router from a script rather than a phone.

All of these are now in `CLAUDE.md`, which is the actual point of keeping that file.

## The Mistake Worth Recording

WF2 had a local, trimmed copy of the AI payload unwrapper that was missing one nesting hop.
The Responses API returns `output[0].content[0].text`, the copy stopped one level short, and a
perfectly correct extraction was rejected as "unexpected shape."

The project's own rules say never to duplicate logic between a library and a workflow. I broke
that rule and it cost an hour. Both workflows now share one implementation.

The related fix was better: the first version of the guardrail happily passed an empty string —
no findings, no problem — and sent a blank email. An empty or unexpected model payload now
throws with the raw shape attached, which is what made the other bugs diagnosable at all.

## Debugging Without The n8n UI

n8n stores executions as a reference-encoded blob that is unreadable by eye. Two techniques
did all the work:

- Parse it as JSON and filter its string entries. Listing which known node names appear tells
  you exactly how far a run got; an error-pattern filter surfaces the real message.
- Numeric-string values are indices back into the same array, so a four-line dereferencer
  resolves them into readable field values.

Also worth repeating: when an AI step misbehaves, call the provider API directly with the same
schema first. One request ruled out the model entirely before any n8n debugging began.

## What I Would Do Differently

- **Read the node source earlier.** Two of the worst bugs — the array-versus-object schema
  field, and the generic-versus-predefined credential type — were five minutes of reading and
  an hour of guessing.
- **Assert the invariant before building the feature.** The empty-email bug existed because
  "the guardrail passed" and "there is something to send" were never the same check.
- **Sequential over parallel by default** in a workflow where one item flows through. The
  parallel branches in WF2 bought nothing and cost the binary-data bug.

## Cost

OpenAI only. A few dollars across the whole build including every failed run.

Everything else — the automation engine, database, mail, forms, scheduling, income
verification, and e-signature — is open source, free tier, or developer sandbox.
